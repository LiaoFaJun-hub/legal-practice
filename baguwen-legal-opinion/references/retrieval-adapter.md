# 检索层适配契约与降级协议

> 本技能**不绑定**任何具体检索后端（MCP / API / 用户粘贴），只依赖一个抽象**检索适配契约**。
> 目的：把"知识层时效与准确"交给外部权威源，同时保证技能不因后端缺失而失效，且**绝不回退到模型记忆**。

## 一、适配契约（Adapter Contract）

任何后端（MCP、HTTP API、用户粘贴的条文）返回给技能时，须满足统一结构：

```
retrieve(query) -> Citation[]   ，其中每条 Citation：
{
  "条文号":   "《劳动合同法》第37条",       # 必填
  "原文":     "劳动者提前三十日……",         # 必填（片段即可）
  "来源标识": "pkulaw_fatiao",             # 必填：哪个MCP/数据库/用户材料
  "效力状态": "现行有效",                    # 强烈建议：现行有效/已修改/已废止/部分失效/尚未生效
  "生效日":   "YYYY-MM-DD",                 # 建议
  "失效日":   null,                         # 建议
  "替代关系": "被《XXX》替代",               # 建议
  "管辖层级": "法律",                        # 建议：法律/行政法规/部门规章/地方性法规/司法解释
  "适用地域": "中国大陆",                     # 建议
  "核验时间": "YYYY-MM-DDTHH:MM:SS"          # 必填：查询时间戳
}
```

**回填规则**：技能把契约返回的四元组 `[条文号][原文片段][来源标识][核验时间]` 注入推理轨；
`效力状态/生效日/管辖层级` 供闸④时效与管辖校验使用。**原文由检索层回填，禁止模型复述**。

## 二、MCP 源映射（可选增强；本机已有）

| 知识库 | 是否宜 MCP | 对接源（示例） |
|---|---|---|
| ① 法条库 | 是（核心） | `pkulaw_fatiao` / `pkulaw_law` / `wk-mcp-law` / `chinese-law` / `moonlit` / `yuandian-mcp-server` |
| ② 要件库 | **否**（方法论资产，内部维护） | 见 [element-library.md](element-library.md) |
| ③ 裁判规则库 | 部分 | 举证责任/证明标准可检索；裁量口径靠类案 |
| ④ 类案库 | 是 | `pkulaw_case` / `courtlistener`（域外） |
| 闸③ 存在性校验 | 是（可外部化） | `pkulaw_cite`（pku_citation_validator）★ |
| 闸④ 时效/管辖 | 部分 | `pkulaw_fatiao` 的效力元数据 + 人工兜底 |
| 域外法 | 是 | 各 `@ansvar/*-law`、`eu/us-regulations` |

> **作用域提醒**：MCP 配置在**项目根 `.mcp.json`**，而技能是**全局**的。
> 运行时须先探测当前项目是否挂载了法律 MCP。

## 三、运行流程（含两态降级）

```
启动 → 探测可用检索后端
   ├─ 探测到（MCP/API 可用）
   │     → 【全检索模式】
   │       阶段一：按概念/争议类型检索【要件框架】（可从 element-library 命中或模型推导并标风险）
   │       阶段二：按要件逐条检索【法条原文】（带效力+时效+管辖元数据）
   │       回填四元组 → 过闸③存在性 → 过闸④时效管辖
   │
   └─ 未探测到 / 检索失败 / 命中=0
         → 显式声明"本次无检索层接入"
         → 切换【仅用户提供模式】
         → 法条一律标 "未检索到，需人工核实"，禁止模型记忆填补（R1）
         → 在第八股存疑清单登记：本分析规范依据未经检索核验
```

**fail-closed 铁律**：MCP 不可用时**绝不回退到模型记忆**。
宁可输出"未检索到"，绝不编造条文——否则接 MCP 反而制造"有检索就敢编"的假象，比不接更危险。

> 说明：在【仅用户提供模式】下，`check_redlines.py` 会稳定报出 1 条 P1（`R1-占位`：核验时间待补）。
> 这是该模式的**预期表现**，不是缺陷——P0 仍应为 0。交付说明中应如实标注"本次无检索层接入，规范依据未核验"。

## 四、双阶段检索（先框架，后条文）

```
案件描述/材料
   → 阶段一：定性检索，命中【要件框架】（争议类型→请求权基础→要件清单→抗辩清单→举证分配→证明标准）
   → 阶段二：取证检索，按要件逐条取【法条原文】+ 司法解释 + 类案（带效力与时效元数据）
   → 锚定与回填：四元组；原文由检索层回填，禁模型复述
   → 存在性校验（闸③）→ 时效管辖校验（闸④）

为什么必须先框架后条文：
  直接检索法条 → 命中"语义相关"条文 → 可能漏掉整个要件维度。
  先取要件框架 → 得到封闭清单 → 后续检索被清单驱动，缺什么一目了然，遗漏可计算。
```

## 五、双源交叉与类案过滤

- **双源交叉**（高价值条文）：对 P0 级引用，用 ≥2 个源（如 `pkulaw_fatiao` + `wk-mcp-law`）比对原文一致性；
  不一致 → 降级为"待核实"，入存疑清单，结论置信度下调。
- **类案"关键事实匹配"后过滤**：向量/文本相似命中的案例可能关键事实完全不同。
  以**关键事实要素匹配**为第一过滤器，"文本相似度"只作排序信号，不作准入条件。
  每个类案须标注"与本案的关键事实相同点/不同点"。

## 六、接入方式（对模型的操作指令）

```
优先：若当前会话可用法律检索 MCP（如 pkulaw_fatiao / chinese-law / wk-mcp-law），
     调用其检索工具获取条文原文与效力状态，并回填四元组。
其次：若用户直接提供条文文本，视为该后端，来源标识记为"用户提供"。
兜底：以上皆无 → 走【仅用户提供模式】，所有法条标"未检索到，需人工核实"。
禁止：凭模型记忆输出任何条文号或原文。
```
